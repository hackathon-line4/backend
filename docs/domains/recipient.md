# recipient — 당사자 기능

**담당:** 조한결
**범위:** 보호자 부르기(R-2), 도움 요청(R-3)과 상세·도착·열람 기록(예외로 이 도메인에 포함)

## 현재 구현

- 당사자 신호·도움 요청 도메인 모델 `recipient_signals` / `help_requests` (#24). API 레이어는 `link` 구현 후 — 생성 API가 `linkId`를 받고, 상세는 사용자 이름이 필요하다
- 두 기록은 **같은 영수증 규칙**을 쓴다. `GuardianReceipt`(임베디드) 한곳에 두었다 — 규칙이 미묘해서 두 군데 적으면 한쪽만 틀리기 쉽다
  - 도착·열람 각각 **처음 시각만** 기록(서버 시각). 같은 보고가 여러 번 와도 값이 밀리지 않는다
  - **열람이 먼저 오면 도착도 같은 시각으로 채운다** (messaging의 "ack 없이 터치가 먼저 오면"과 같은 패턴)
  - 첫 열람일 때만 `markOpened`가 `true`를 돌려준다 — 도움 요청의 재알림 중단과 '확인함' 발송을 한 번만 하기 위해서다
- 도움 요청의 위치
  - 위치 공유가 꺼져 있으면(`NOT_SHARED`) 좌표가 와도 **저장하지 않는다**
  - 못 얻었으면 기다리지 않고 `PENDING`으로 먼저 보내고 나중에 붙인다. **`PENDING`일 때만** 붙일 수 있고 한 번 정해지면 `LOCATION_ALREADY_SET`
  - 좌표는 `double`이 아니라 `BigDecimal(9,6)`이다. 소수점 6자리가 지도에 찍히는 값이라 반올림 오차가 남으면 안 된다
  - 주소는 서버가 나중에 채우고, 바꾸지 못하면 `null`로 둔다
- 데이터 모델 초안에는 `link_id`만 있지만 보낸 사람·받는 사람 UUID를 함께 둔다 — 연결을 거치지 않고도 "내 기록인지" 판단하기 위해서다(messaging의 `Message`와 같은 이유)
- **Hibernate는 임베디드의 모든 컬럼이 null이면 필드를 null로 되돌린다.** 아직 아무도 받지 않은 기록을 다시 읽으면 `receipt`가 null이 되어 다음 보고에서 NPE가 난다 — 쓸 때마다 되살리는 접근자를 거친다. `CapturedLocation`도 같은 성질이지만 그쪽은 "위치 없음"이 의미 있는 상태라 그대로 둔다

- 도착·열람 기록 2종 (#31): `POST /recipient-signals/{id}/receipts` · `POST /help-requests/{id}/receipts`. 이 연결의 보호자만
  - 푸시 수신 핸들러가 중복 호출될 수 있어 같은 보고가 여러 번 와도 안전하다
  - 역할이 다르면 403, 내 기록이 아니면 404(존재 자체를 숨김)
  - 첫 열람 여부를 서비스가 돌려준다 — 재알림 중단과 `HELP_CONFIRMED` 발송을 걸 자리이고, 푸시 구현 후 채운다

- 도움 요청 상세 `GET /help-requests/{id}` (#67). 보호자만, 내 요청이 아니면 404
  - **열람을 기록하지 않는다.** 조회와 기록을 나눠 둬서, 화면이 상세를 다시 열어도 '열어 본 시각'이 밀리지 않는다 — 기록은 `POST /help-requests/{id}/receipts`가 한다
  - `followingMessages`는 요청 이후 보호자가 보낸 신호를 **다음 도움 요청 전까지** 최대 20건 준다. 그 뒤 신호는 다음 요청에 딸린 대화라 끊는다
  - messaging 조회는 `MessageQueryService.sentBetween`을 거친다 — 권한은 부르는 쪽이 이미 확인했으므로 거기서 다시 묻지 않는다. 연습(`PRACTICE`)은 주고받은 신호가 아니라 제외한다

- 도움 요청 첫 열람에 당사자에게 `HELP_CONFIRMED` 푸시를 보낸다 (#71). **첫 열람에서만** — 상세를 다시 열 때마다 '확인함' 진동이 울리면 안 된다

### 후속 작업 (해당 기능 구현 시)

- 엔드포인트 4개 — `link` 도메인 구현 후(생성 2개가 `linkId`를 받는다)
- 도움 요청 상세의 `sender.name`, `followingMessages`(요청 이후 보호자가 보낸 신호 최대 20건) — `account` 이름 조회와 `messaging` 조회가 필요
- `HELP_REQUEST` 재알림 타이머(1분 간격 최대 5회) — 열람되면 중단. messaging 타이머와 같은 구조로
- 주소 변환 — 지도 API 업체·키 미정
- 10분이 지나도 `PENDING`이면 `UNAVAILABLE`로 바꾸는 타이머

## Pending Decisions

- **도움 요청 재알림**: 1분 간격, 최대 5회(백엔드 제안), 열람(`OPENED`) 기록되면 멈춤. — 기획 확인 필요.
- 당사자가 보낼 수 있는 신호 종류: 보호자 호출, 도움 요청(긴급) 두 가지로 제안됨 — 이미 확정에 가까움, 최종 확인만 필요.
- **위치를 끝내 못 받았을 때**: 10분이 지나도 `PENDING`이면 서버가 `UNAVAILABLE`로 바꿈(백엔드 제안). 10분이 확정값이 아니라 아직 구현하지 않았다. — 기획 확인 필요.
